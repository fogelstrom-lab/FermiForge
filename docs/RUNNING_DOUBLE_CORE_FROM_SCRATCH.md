# Starting a double-core iteration without an imported field

FermiForge can now construct and begin relaxing a nonaxisymmetric double-core
candidate without reading any archived order-parameter or mean-field data. The
first implementation is deliberately a small, reproducible integration case;
it establishes the initialization and nonlinear-solver path, not a converged
physical double-core result.

## Seed definition

The initializer is based on the London model in Eq. (4) of `dcvlong.pdf`. Put
the half cores at `(0,+a/2)` and `(0,-a/2)` and define regularized complex
phases

```text
u_+ = [x + i(y-a/2)] / sqrt[x^2 + (y-a/2)^2 + xi_c^2],
u_- = [x + i(y+a/2)] / sqrt[x^2 + (y+a/2)^2 + xi_c^2].
```

The branch-free combinations occurring in the London matrix are

```text
exp(i phi) cos(delta) = (u_+ + u_-)/2,
exp(i phi) sin(delta) = (u_+ - u_-)/(2i).
```

They are placed in `A_xx=A_zz`, `A_zx=-A_xz`, exactly following the
spin-rotation form of the London model. Its discontinuous `A_yy` type-10 wall
is replaced by a continuous winding-one field suppressed over a configurable
finite wall width. This regularization provides two pair-density minima and a
planar-filled center while approaching `Delta exp(i phi) I` far from the core.

The three Fermi-liquid current-related mean fields start from zero. They are
generated by the first quasiclassical map, rather than copied from the archived
double-core solution. The initial analytic formula and its regularization are
isolated in `src/double_core_seed_2d.f90` and have a direct regression test.

## Laptop iteration

From the project directory:

```text
tools/run_double_core_from_scratch.py
```

If `work/strict-point-map-build` already contains the current executable:

```text
tools/run_double_core_from_scratch.py \
  --no-build \
  --build-dir work/strict-point-map-build
```

The default input is `examples/2d_double_core_from_scratch_smoke.nml`. It uses:

- a 29 by 29 three-zone multiscale mesh extending to `12 xi0`;
- half cores initially placed at `y=+/-2 xi0`;
- a centered active disk of radius `3 xi0`, containing 113 nodes;
- 32 azimuthal by 11 polar directions and eight Ozaki poles;
- the Eq. (20)-constrained order-parameter tail, two-power Fermi-liquid tail,
  and dependent outer halo;
- gauge, translation, and coordinate-orientation tangent projection;
- up to 20 Anderson updates on ten MPI ranks; and
- a restartable sparse checkpoint after every completed update.

No file under `2D_benchmarks` is read. The only numerical input tables are
`new_src/gauss11.dat` and `new_src/ozaki.dat`, which define the quadratures at
`T/Tc=0.30`.

At roughly 30 seconds per map on the reference MacBook Pro, the default run
takes about ten minutes if it reaches the 20-update limit. The program prints
one `solved (double-core AA)` record per completed update. That record contains
the average and maximum projected update errors, Anderson mixing `p`, retained
history depth `md`, and map time. `iteration_history.dat` is flushed after
every update, so it remains inspectable while the calculation is running.

Each invocation creates a timestamped directory under `runs/` containing the
exact input, log, initial and final full fields, the latest per-update sparse
checkpoint, a separate sparse final state, sampled residuals, iteration
history, metrics, JSON acceptance report, and thirteen PNG figures. The figures
use the common white-to-indigo amplitude scale and the blue-white-red
phase/current scale.

`plots/double_core_axis_profiles.png` is the FermiForge counterpart of Fig. 4
in `dcvlong.pdf`. It samples all non-negligible real and imaginary Cartesian
order-parameter components on the positive symmetry axes. As in the original,
the positive x axis runs inward from the left and the positive y axis runs
outward to the right. The profiles are normalized by a robust outer-boundary
estimate of the bulk gap. Its upper row is the analytic seed and its lower row
is the state after the completed updates. Colour-blind-safe black, vermillion,
and blue encode spin rows; line style encodes orbital columns; open-circle
markers distinguish imaginary parts from real parts.

`plots/double_core_structure_history.png` follows the two pair-amplitude
minima on the y axis after every accepted update. It plots their positions,
the measured separation `a`, the two minimum amplitudes, and the center
amplitude. The same separation appears as `a=` in each live terminal record.
This provides an immediate branch diagnostic: collapse of `a` toward the
smallest grid separation indicates evolution toward a single-core state.

For a short integration check, override the new default explicitly:

```text
tools/run_double_core_from_scratch.py --iterations 2
```

## Overnight double-core calculation

The larger calculation intended for a ten-core MacBook Pro is:

```text
caffeinate -i tools/run_double_core_overnight.py
```

`caffeinate` prevents idle sleep while the foreground calculation is active.
Keep the terminal open. The dedicated preset uses:

- a `[-40,40] x [-40,40] xi0` computational cell;
- 119 by 119 multiscale mesh points;
- `0.4 xi0` spacing throughout the central `[-14,14]^2 xi0` square;
- `0.8 xi0` intermediate and `2 xi0` outer target spacing;
- half cores initially at `y=+/-10 xi0`;
- a self-consistent disk of radius `22 xi0`, containing 7,249 points;
- an asymptotic fitting annulus beginning at `26 xi0` and matching at
  `32 xi0`;
- 152,229 real values in the Anderson vector; and
- at most 20 updates, checkpointed after each accepted update.

Scaling from the verified 113-point calculation gives a rough expectation of
30--40 minutes per map, or about 10--14 hours for all 20 updates. The actual
time should be read from the first printed `map[s]` value; trajectory length
and interpolation make point-count scaling approximate.

This preset deliberately changes three controls together: cell size, hard-core
resolution, and initial half-core separation. It is designed to test whether
the apparent drift toward the A-phase core was a finite-cell/basin effect. It
does not prevent a physically preferred A-phase core from winning.

To stop after a shorter timing trial, use:

```text
tools/run_double_core_overnight.py --iterations 1
```

The full run can be continued from the checkpoint without changing the mesh:

```text
caffeinate -i tools/run_double_core_overnight.py \
  --sparse-restart /absolute/path/to/sparse_checkpoint_state.dat
```

Anderson history starts anew after a restart, while the full active physical
state is restored.

## Extend the converged state along the double-core axis

The first 20-update large run showed that the positive-y axis profiles reached
the edge of the circular self-consistent region at `22 xi0`, while the
positive-x profiles were already well contained. The residual maximum was
also close to that boundary. This is evidence for an active-domain cutoff,
not a need to refine the whole `[-40,40]^2 xi0` cell. In particular, the
visible cutoff occurs at the active radius `22 xi0`, not at the fine-to-medium
mesh transition at `14 xi0`. The staged calculation tests domain extent first;
if its profiles expose resolution error in the `14--28 xi0` band, anisotropic
mesh refinement is the next separate change.

The production continuation therefore does not prescribe the next radius.
Run the adaptive controller with:

```text
caffeinate -i tools/run_double_core_adaptive_domain.py
```

It finds the newest overnight checkpoint, infers its current active radii from
the run metrics, and measures two quantities independently in the x and y
directions:

- amplification of the field step where the active region meets the inactive
  region, relative to ordinary interior mesh-to-mesh variation; and
- the RMS residual in the outer active collar relative to the inner-core RMS.

Only a failing direction is enlarged. Growth is multiplicative, with at least
one local mesh interval added, so neither temperature nor pressure appears in
a prescribed physical radius. They affect the selected size through the
self-consistent fields and residuals. The asymptotic fitting and matching
surfaces are nested ellipses moved with the active boundary in units of the
local mesh spacing. At each angle, their radial intersections define the two
source radii. The order parameter obeys the Eq. (20) block powers, while both
`1/r` and `1/r^2` coefficients are fitted for each Fermi-liquid mean-field
component. Every point outside the active ellipse is regenerated after an
accepted update; there is no frozen collar.
The controller stops when both directions pass, or reports `cell_limit` when
the physical mesh must be enlarged before a trustworthy asymptotic guard can
be retained.

The current overnight state illustrates the decision. Without a new field
map, the diagnostics accept x but reject y: the interface amplification is
`2.27` versus `8.09`, and the boundary/core residual ratio is `0.195` versus
`0.281`. The default provisional limits are `3.0` and `0.25`. All limits,
growth factors, and block lengths are recorded in the JSON report and can be
changed explicitly rather than being hidden physics constants.

Inspect the decision without starting MPI work with:

```text
tools/run_double_core_adaptive_domain.py --diagnostics-only
```

A nonzero exit status in this mode means that at least one direction needs
growth. To use an explicit checkpoint or a different relaxation block:

```text
caffeinate -i tools/run_double_core_adaptive_domain.py \
  --restart /absolute/path/to/sparse_checkpoint_state.dat \
  --block-iterations 10
```

Each accepted update is checkpointed and every adaptive stage produces its own
axis-profile plot. Resume an interrupted adaptive calculation by passing its
latest checkpoint to the same command. The resulting
`adaptive_domain_report.json` contains the directional diagnostics, chosen
radii, common-checkpoint field changes, stopping reason, and restart paths.

The short end-to-end check for the anisotropic continuation itself is:

```text
tools/run_double_core_from_scratch.py \
  --input examples/2d_double_core_elliptical_asymptotic_smoke.nml \
  --iterations 1 --no-plot
```

It uses an active `5 x 6 xi0` ellipse, an inner fit ellipse of `3 x 4 xi0`,
and a matching ellipse of `4 x 5 xi0`. The test exercises a complete MPI map,
Anderson update, bulk-reference refresh on the matching ellipse, and dependent
halo reconstruction of both the order parameter and Fermi-liquid self-energy.
Production adaptive inputs use `checkpoint_scope = 'full_state'`: cells in the
current dependent halo are saved too, because they become independent unknowns
if a later stage enlarges the active ellipse. The controller converts the
full-field output of older update-only checkpoints automatically before its
first growth stage.

For a controlled production continuation that tests the corrected asymptotic
update without changing the current active domain, use:

```text
caffeinate -i tools/run_double_core_adaptive_domain.py \
  --hold-domain \
  --block-iterations 20 \
  --maximum-stages 1 \
  --ranks 10 \
  --jobs 10 \
  --build-dir work/double-core-scratch-build \
  --no-build
```

The controller prefers the largest available checkpoint before recency, so a
compact smoke test cannot displace the 119 by 119 production state. Passing an
explicit `--restart` remains the reproducible choice. `--hold-domain` keeps the
current `22 x 27.5 xi0` active ellipse and builds guarded `18.8 x 24.3 xi0`
inner and `20.4 x 25.9 xi0` matching ellipses. These remain within the present
medium-resolution region. The bulk reference is the fixed theoretical
`Delta_B exp(i phi) I`; only the tail coefficients and self-consistent fields
change during iteration.

Each production map also evaluates up to eight passive mesh points on each of the
positive and negative x and y rays between the active ellipse and the physical
mesh edge. These points use the complete quasiclassical trajectory map, but
are excluded from the Anderson vector. The run stores both the imposed input
state and the freshly mapped state in `asymptotic_probe_states.dat` and writes:

```text
plots/double_core_asymptotic_probe_harmonics_x.png
plots/double_core_asymptotic_probe_harmonics_y.png
plots/double_core_asymptotic_probe_mean_field.png
plots/asymptotic_probe_diagnostics.json
```

In the figures the dotted curves are the imposed Eq. (19)--(20) tail and the
marked curves are the absolute mapped-minus-imposed difference. Thus the
marked curves are an independent self-consistency test, rather than another
plot of the stored continuation. They should become small compared with the
dotted tail as the source surfaces, active domain, and solution become
consistent. Each harmonic title reports the complex relative RMS
map-minus-tail mismatch when the imposed bulk-subtracted tail is resolvable.
For a symmetry-zero tail it reports the absolute RMS normalized by the bulk
gap instead. The JSON report records the imposed-tail RMS, the residual RMS,
and the relative value (or `null`) separately.

The production overnight inputs add a second, stronger check after the main
solve has stopped. Exterior ray points are copied to an independent shadow
state and relaxed with their own
Anderson history. The production field, checkpoint, endpoint fit, and main
iteration history are frozen throughout this calculation. The shadow solve
writes:

```text
asymptotic_probe_history.dat
asymptotic_shadow_states.dat
plots/double_core_asymptotic_shadow_harmonics_x.png
plots/double_core_asymptotic_shadow_harmonics_y.png
plots/double_core_asymptotic_shadow_mean_field.png
plots/double_core_asymptotic_shadow_convergence.png
plots/asymptotic_shadow_diagnostics.json
```

The dotted curve in each harmonic panel is the imposed bulk-subtracted
asymptotic field. The dash-dot open markers show the first map defect
`F(B)-B`, where `B` is that imposed field. The solid filled markers show the
independently relaxed correction `S*-B`; this is the direct estimate of the
extrapolation error. Dashed crosses show the terminal defect `F(S*)-S*` and
must become small before the correction can be trusted. A small terminal
defect with a small correction is positive evidence for the extrapolation; a
small terminal defect with a large correction means that the exterior problem
converged but disagrees with the imposed tail.

The run report keeps numerical execution success separate from physical
validation. `asymptotic_validation_status` is `passed` only when both the
production solve and the held-out solve report convergence. If the shadow
solve converges first, its result is labelled
`provisional_production_not_converged`; reaching the configured shadow
iteration limit is labelled `shadow_not_converged`. The global shadow-mask RMS,
maximum, relative-L2 defect, and tolerance are also copied into the shadow
JSON report.

The default diagnostic updates isolated ray points while all neighbouring
interpolation nodes remain at the extrapolated values. This avoids creating an
artificial finite normal inclusion in the coarse exterior mesh. A nonzero
`asymptotic_probe_iteration_stencil_radius` is available as a sensitivity test,
but its result depends on the physical size of that patch. Set
`asymptotic_probe_iterations = 0` to disable the extra maps. The compact smoke
input uses two shadow updates; the overnight inputs allow twelve.

The deterministic two-stage command remains available as a reproducibility
test of the original `22 x 28` and `22 x 34 xi0` proposal:

```text
caffeinate -i tools/run_double_core_y_extension.py
```

It is not the production sizing policy. The present controller adapts the
active domain inside an existing mesh. Automatic cell enlargement and
interpolating a checkpoint onto a newly generated mesh remain a separate
adaptive-remeshing step.

## Historical `dop` comparison

The historical initializer supplied in
`new_src/how_I_initialise_the_different_cores.f` is available independently of
the London seed. Run the same large mesh and solver controls with that seed via:

```text
caffeinate -i tools/run_historical_dop_overnight.py
```

This calculation does not prescribe separated half cores. It starts from the
historical centered diagonal vortex plus the twofold
`A_zx=-A_xz proportional to cos(phi)^2` perturbation and lets the separation
emerge dynamically. The London and historical-`dop` outputs therefore form a
controlled comparison of branch preservation versus spontaneous splitting.
The exact transcription and the selectable `nop`/`aop` alternatives are
documented in `docs/HISTORICAL_CORE_SEEDS.md`.

## Verified short result

The first complete ten-rank smoke run took about one minute for its two maps and
reported:

```text
grid                                  29 x 29
active update points                  113
dependent asymptotic halo points      340
seed pair amplitude at center         0.21219
seed pair amplitude at each half core 0.15846
maximum update residual, map 1        6.881e-2
maximum update residual, map 2        6.849e-2
Anderson mixing after map 2           0.670
maximum normalization error           1.67e-15
terminal status                       iteration_limit
JSON acceptance                       passed: true
```

The sizeable residual is expected: the analytic London field is a starting
guess, not a self-consistent quasiclassical solution. The small decrease over
two maps only verifies that iteration has begun normally.

## Continue from the sparse checkpoint

The complete active state can be overlaid on a newly generated analytic seed:

```text
tools/run_double_core_from_scratch.py \
  --iterations 20 \
  --sparse-restart /absolute/path/to/sparse_final_state.dat
```

The runner counts the checkpoint records and requires the executable to report
that every record was applied. Anderson history is intentionally reset at a
new run. In the verification restart, all 113 active records were applied; the
next map's sample relative-L2 residual was `3.64e-2`, compared with `1.10e-1`
on the second map of the original analytic-start run.

During a long run, use `sparse_checkpoint_state.dat` from its timestamped run
directory. It is replaced only after a complete accepted update, so an
interrupted trajectory map leaves the preceding valid checkpoint available.
The checkpoint cadence can be changed or disabled with, for example,
`--checkpoint-every 5` or `--checkpoint-every 0`.

## What remains before calling this a double-core solution

The default calculation freezes analytic seed values between the active disk
and the asymptotic matching circle. It also uses a deliberately small initial
half-core separation and reduced azimuthal quadrature. The next controlled
calculation must therefore:

1. enlarge the centered active radius until it reaches the fitting annulus;
2. refine the core and intermediate soft-texture zones;
3. continue the half-core separation, temperature, and `F1s` toward the
   archived benchmark values;
4. iterate each stage to the stated residual tolerance;
5. compare the resulting fields, half-core separation, current, and
   asymptotic coefficients with the imported legacy solution; and
6. repeat from the independent axial-vortex symmetry-breaking seed required
   by the project plan.

Until those gates pass, output from this workflow should be called a
from-scratch double-core candidate or iteration, not a converged double-core
vortex.
